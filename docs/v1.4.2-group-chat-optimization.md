## 1. 报告目标

本轮优化不以“代码结构更漂亮”为首要目标，而以三个真实体验指标为核心：

1. 用户明确或隐式在和 Bot 说话时，Bot 不应漏回。
2. 多人、多话题交错时，不应频繁串话题、认错收件人。
3. Bot 不应因为模糊的语义相关性而随意插入人与人之间的聊天。

因此重点不是增加更多规则、更多 RAG、更多 LLM 判断，而是重新明确三个相互独立的问题：

```text
Recipient     这句话在对谁说？
Topic         这句话属于哪个讨论上下文？
Participation Bot 此刻应该不应该说话？
```

## 2. 总体结论

v1.4.1 已具备 Conversation DAG、reply/mention/inferred parent、topic profile、
hashed 语义匹配、神经 embedding、topic reranker、归档话题召回、active interlocutor、
addressivity、pending hover、debounce、persona 模式、arbiter、标注 UI。

功能数量已经足够，真正的问题是：

> Recipient、Topic、Participation 三个概念之间的边界不够清楚。

尤其存在以下结构性问题：

```text
ThreadRouter        → 推断 recipient
AddressivityRouter  → 再次推断 recipient
MessageSemantics    → 重新解释 recipient certainty
PersonaEngine       → 再次判断“是不是在对我说”
Main fast path      → 又自己判断一次 Bot name / strong address
```

后果是同一个明确的 Bot 收件人可能被逐层降级，最终 Bot 沉默。v1.4.2 的核心方向：

> 先统一 Recipient 契约，再让 Topic 与 Participation 分别消费它，而不是继续让多个
> 模块独立猜“是不是对 Bot 说”。

## 3. v1.4.1 的核心缺陷与本版处置

### 3.1 Topic ambiguity 污染 Recipient ambiguity

旧逻辑近似：

```python
ambiguous = topic_ambiguous or addressee_confidence < 0.72
```

Addressivity 的 STRONG 判断要求 `not ambiguous`，于是话题归属不确定会否决已经明确的
Bot 收件人，降级为 HOVER，`is_bot_targeted=False`，Bot 沉默。这是语义层级串线。

本版拆成独立字段，并在消费侧提供唯一读取入口：

```python
# core/routing_contract.py
def addressee_is_ambiguous(routing, default=False) -> bool: ...
```

- 路由输出 `topic_ambiguous` 与 `addressee_ambiguous` 两个独立结论。
- Recipient 判断只读 `addressee_ambiguous`；Topic 判断只读 `topic_ambiguous`。
- 旧快照缺少新字段时按“先置信度、后聚合字段”的顺序兼容，避免误读历史数据。
- 原 `ambiguous` 仍然保留，但只用于诊断、回放与异步路由升级（`rerank_pending`、
  topic reranker），不再是收件人证据。

### 3.2 Bot 身份识别多套实现

旧代码中 AddressivityRouter、ThreadRouter、main 快路径、MessageSemantics、
PersonaEngine、Arbiter 各自判断“Bot 是否被叫到”，规则不一致。例如 Bot 名 = `助手`，
文本 `这个助手席怎么拆？`，宽松实现会命中子串，严格实现不会。结果是“结果正确、
原因错误”，而错误原因还会继续流向 message semantics、prompt、dashboard、pending hover。

本版统一到 `core/bot_identity.py`：`BotIdentityMatcher` 是唯一的 Bot 身份解释入口，
`main.py` 快路径、`AddressivityRouter._name_mentioned_in_text`、
`RecipientResolver` 全部改为调用它。

### 3.3 Subject 与 Addressee 的语义污染

群聊必须区分 `Addressee`（我在对谁说）与 `Subject`（我在说谁）。
`群间刚才说的方案不太对` 是讨论对象，不是呼语；`群间，你刚刚为什么这么说？`
则同时是呼语与对象。本版让两者各自独立推断、各自拥有证据，不再用“名字是否出现”
机械推导：

```python
@dataclass(frozen=True)
class BotReference:
    mention: bool = False
    vocative: bool = False
    subject: bool = False
```

三者可以同时为真，不是单选枚举。

### 3.4 多收件人模型不完整

`@小明 群间你怎么看？` 的自然语言意义是 `recipient = [小明, Bot]`；旧路径看到
`@小明` 后直接形成 `recipient = 小明`，Bot name 没有机会参与判定。反方向
`@Bot @小明 你怎么看？` 会丢掉第二个收件人。

本版正式支持 `recipient_ids: tuple[str, ...]`：显式 @、平台唤醒、呼语按证据合并为
一个集合，Bot 只判断“是否在集合内”，不再假设唯一收件人。

## 4. 优化前架构

```text
Group Event → main.py ingress（fast/debounce）
            → Conversation DAG
            → ThreadRouter（topic + parent + addressee）
                 ├── TopicResolver / Embedding
                 ├── AddressivityRouter（再次判断身份）
                 ├── MessageSemantics（再次解释 certainty）
                 └── PersonaEngine（再次判断是否对自己说）
            → InterventionArbiter → Native Agent → Response
```

核心问题是“是不是在对 Bot 说”不由一个模块决定，而是被五处分别推断，导致重复判断、
规则不一致、字段语义污染、阈值重复、调参困难、回归难定位。

## 5. 目标架构

```text
Group Event → Event Normalize（mentions/reply）
            → BotIdentityMatcher（MENTION / VOCATIVE / SUBJECT / NONE）
            → Conversation DAG
            → RecipientResolver（这句话到底在对谁说？）
                 recipient_ids / bot_targeted / confidence
                 addressee_ambiguous / subject_ids / evidence
                 ├── TopicResolver（在聊什么？）
                 │     topic_id / topic_confidence / topic_ambiguous
                 └── ParticipationPolicy（Bot 该不该说话？）
                       STRONG / HOVER / WEAK
            → InterventionArbiter
            → Canonical Context Builder（唯一 payload）
            → Native Agent / LLM → Response

            Decision Trace / 回放导出 / 人工标注（旁路，只读）
```

本版的实际调用顺序仍保留“Topic/Parent 先产生候选、Recipient 再消费”的现有链路
（见 [实施记录](group_chat_optimization.md)），未宣称已经实现无循环的全新拓扑；
解耦目标是**契约与所有权**，而不是重排调用图。

## 7. RecipientResolver 契约

`core/recipient_resolver.py`：

```python
@dataclass(frozen=True)
class RecipientInference:
    recipient_ids: tuple[str, ...]
    confidence: float
    bot_targeted: bool
    bot_confidence: float
    subject_user_ids: tuple[str, ...]
    bot_is_subject: bool
    evidence: tuple[str, ...]
    parent_override: Optional[Tuple[str, float, str]] = None
```

- 结果不可变（`frozen`），调用方不能就地改写；已有测试断言 resolver 不修改 DAG、
  不写 `pending_hover`、不写 `active_dialogue`。
- 优先级：显式 @/平台唤醒/呼语合并 → 引用（含“引用他人但在对 Bot 说话”子情形）
  → 高置信推断父消息 → 有限度的进行中对话续接。
- `addressee_ambiguous`、`explicit` 由契约派生，而不是各调用方自行解释。

Topic 另行输出，禁止跨层合并：

```python
@dataclass(frozen=True)
class TopicInference:      # 目标契约
    topic_id: str | None
    confidence: float
    topic_ambiguous: bool
    pending: bool
```

当前 `TopicInference` 尚未独立成类，`topic_*` 字段仍由 `RoutingInference` 承载；
但“禁止 `ambiguous = topic_ambiguous or recipient_ambiguous` 被下游读取”已经落地。

## 8. BotIdentityMatcher

```python
class BotReferenceType(Enum):        # 目标命名
    NONE = "none"
    PLATFORM_MENTION = "platform_mention"
    VOCATIVE = "vocative"
    SUBJECT = "subject"

BotIdentityMatcher.match(text, names, mentions=..., bot_id=...)
  -> BotReference(mention: bool, vocative: bool, subject: bool)
```

- `mention` 只来自平台 @ 组件或 Bot ID，不做字符串推断。
- `vocative` 要求句首/标点后的称呼结构、命令或问句模式、或整体仅为称呼。
- `subject` 要求名字具有独立边界并带谓词语境；纯子串不算。
- `strip_vocative` 只删除识别到的呼语跨度；`strip_leading_name` 只删除一处句首名字
  （用于度量“称呼之后还剩多少内容”）。二者取代旧的 `text.replace(bot_name, "")`。

## 9. 一字中文 Bot 名

旧实现 `if len(name) < 2: return False` 会整体放弃单字昵称，改成
`if name in text: return True` 又会把 `显卡`、`好卡` 当呼唤。本版用结构规则：

```text
Bot 名 = 卡
@卡            → 命中
卡，帮我看一下   → vocative
卡你怎么看？     → vocative
这个游戏好卡     → NONE
显卡怎么选       → NONE
```

即：句首或标点后、呼语结构、命令/问句模式，三者之一才成立。

## 10. ParticipationPolicy

RecipientResolver 只回答“谁是收件人”，ParticipationPolicy 只回答“Bot 是否值得开口”。
目标第一层必须是硬证据：

```python
if recipient.bot_targeted and not recipient.addressee_ambiguous \
        and recipient.confidence >= explicit_threshold:
    return STRONG
if recipient.recipient_ids and not recipient.bot_targeted \
        and recipient.confidence >= explicit_threshold:
    return WEAK
# 只有 recipient 模糊时，才进入连续性软证据
```

本版已落地的部分：`AddressivityRouter` 在 `routing_schema_version == 2` 且收件人明确时
直接依据契约返回 STRONG/WEAK，不再重复推断身份、不再被话题歧义否决；话题置信度作为
`topic_relevance` 传给下游。未落地的部分：仍未抽出独立模块，软证据仍由 Addressivity
内部的时间衰减、语义连续性、人类引用惩罚计算，未引入证据族权重。这是有意的推迟（§11）。

## 11. 证据族与聚合

多个因素高度相关（same thread、active interlocutor、inferred parent、continuation、
time proximity），直接相加会重复计算，而 `max()` 会丢掉“多个弱证据相互佐证”。
目标做法是按族聚合，例如：

```text
Explicit Recipient / Dialogue Continuity / Semantic Continuity
Temporal Continuity / Participant Continuity / Negative Evidence

dialogue = min(1.0, 0.45*parent + 0.25*same_thread
                    + 0.20*active_interlocutor + 0.10*continuation)
或 noisy-OR: 1 - ∏(1 - evidence_i)
最终权重用带单调约束的 logistic regression 从标注数据拟合，
冻结为版本化配置（weights_version）。
```

**本版不做**：只有 14 个合成场景，不足以拟合权重；在没有真实标注前调整软证据会同时
改变漏判与误插话两个方向。当前最新观察（[当前报告](routing_current.json)）：

```text
bystander_short_followup
  Bot → A 之后 B 立刻说“真的假的”
  recipient: 未确定（bot_targeted=False，persona 不认领）
  addressivity: hover (0.65) → 静默缓冲，不立即回复
```

也就是说“旁观者续接”不会立刻换取回复，但会进入 Safe Hover 缓冲。是否应把
“Bot 正在和谁对话”提升为硬证据、从而抑制该 hover，属于 ParticipationPolicy 工作，
必须在第 3 节的两向指标（漏判 / 误插话）同时具备基线后再改。

## 12. Active Dialogue 应成为正式状态

```text
Bot → A：你用什么版本？
A：1.21.4        ← 没有 @、没有引用、没有 Bot 名，但几乎一定是在回答 Bot
```

目标结构：

```python
@dataclass
class ActiveDialogue:
    user_id: str
    topic_id: str | None
    last_bot_message_id: str
    last_user_message_id: str | None
    last_bot_was_question: bool
    updated_at: float
    confidence: float
```

本版以 `last_bot_node` + `last_interlocutor` + 话题一致性 + 时间窗 + 无竞争发言者的
组合实现了等价判定（`active_interlocutor_followup`，置信度 0.76），但**没有**独立
`ActiveDialogue` 结构，且 `last_bot_was_question` 仍是隐含条件。这是已知缺口：
“Bot 提问后等待回答”尚未成为显式高价值状态。

## 13. 对话连续性不能只看时间

不要仅用“过去多少秒”判断连续性，必须同时考虑：

```text
elapsed_seconds / intervening_message_count / intervening_user_count
topic_changed / last_bot_was_question
```

`30 秒无人发言` 与 `10 秒内 6 个人发了 15 条` 含义完全不同。本版在 RecipientResolver
的续接分支中已要求“无中间竞争发言者”（`competing`），并在 decision trace / dashboard
中记录 `intervening_users` 计数；更完整的参与度聚合仍待 §11。

## 14. Topic 优化策略

目标顺序是**先修画像构建开销，再决定是否需要 Top-K**。Top-K shortlist 会改变候选召回：
低词面重叠但由对话血缘或神经语义胜出的候选可能被剪掉。在没有 R@K 证据前不引入默认
shortlist。若未来上线，必须先测：

```text
R@3 / R@5 / R@6
同义改写 / paraphrase / 旧话题 reopen / 低词面高语义相似
```

以及最终话题准确率、显式引用保持率、真实话题规模下的延迟。**v1.4.2 不改默认召回。**

## 15. Topic Profile 与 revision

提议是在状态变化时递增 `profile_revision`，读取时才懒重建。核查结论：当前实现已经有
话题画像缓存，指纹覆盖实际节点内容、收件人、父消息、可用历史节点集合、provider 代次、
维度与向量，重指派/淘汰/路由变化/向量预热都会失效对应视图，`remember` 也只重建受影响
的话题。因此本版**没有**再加 `profile_revision` 计数器，避免两套失效机制并存。

本版只做两处输出等价优化：神经评分路径不再计算随即被丢弃的 hashed 查询向量；评分不再
重复 `rebuild_profile` 已经做过的时间窗过滤。

**不做真正增量 centroid**：以下路径都会影响画像——message append、reassignment、
pending→committed、prune、archived reopen、embedding late arrival、parent correction。
任一遗漏都会造成 `sum_vector` 长期漂移，极难排查。维持 revision/指纹 + 懒全量重建。

## 16. Embedding 职责与执行

Embedding 应主要解决“这句话和哪个 Topic 相关 / 最可能接哪条历史消息 / 旧话题是否
reopen”，不应直接解决“用户是不是在叫 Bot”。`你觉得呢？然后呢？为什么？` 这类短句
没有独立语义，必须依赖 dialogue state、parent、reply、participant continuity、
intervening users。

同文本 single-flight、有界向量 LRU 是既有能力。本版新增：

- **执行上限**：不同文本的未完成请求上限 8（构造可覆盖），超出立即返回 `None` 走
  hashed 回退，不排队；同文本等待者仍共享已准入请求。
- **代次隔离**：请求创建时捕获 generation，重配置后过期结果与过期异常都不能写回当前代次，
  包括 provider 暂时吞掉取消的情况。
- **归属清晰**：`SemanticMatch.backend` 记录本次匹配的来源（`hashed` / `neural`），
  不再依赖共享的 `last_backend`。

不缓存 provider 对象：宿主热替换 provider 后继续使用旧实例风险更大。

## 17. should_link 的定位

生产路径不调用 `EmbeddingAdapter.should_link()`；它依赖 `last_backend` 共享状态是
坏 API 设计，但不是当前群聊表现问题。本版把它改为消费 `match.backend` 的纯函数语义
（结果自证来源），保留兼容；`last_backend` 仍作为状态面板的诊断字段。

## 18. Prompt Context 与 Canonical Context Builder

两份 context 并非完全重复：一份带 `background_conversation_data`、`attribution_note`、
`social_hint` 与完整 `n.text`；另一份措辞不同、有 1200 字截断、routing context 不同。
因此不能简单地“自有请求就跳过全部 context”。

本版落地 `core/conversation_context.py`：

```python
build_conversation_context(dag, trigger_node, bot_id="") -> dict
# current_turn / message_semantics / background_conversation_data
# attribution_note / social_hint
```

- 自有请求与宿主 hook 共用同一份 payload，`message_semantics` 与
  `background_conversation_data` 不重复，每条背景消息统一截断 1200 字。
- 自有请求标记 `_chat_dynamics_owned_request` 后，hook 只跳过**重复的会话归属注入**；
  vibe、自学习、媒体提示、人设与宿主 hook 全部保留。
- `attribution_note` 明确 `sender_id` 是发送者、`recipient_ids` 是收件对象、
  `certainty=possible` 只是话题推测、`unknown` 不代表在对 Bot 说话。

## 19. Persona 与 Legacy 必须分别验证

系统存在 legacy 与 persona 两条决策链，persona 有自己的 recipient 消费逻辑。所有关键
golden 用例在两侧各跑一遍，报告输出两个混淆矩阵；`should_reply` 在人设路径由
`PersonaEngine` 在模型决策与参与闸门之后补全，其余时刻保持 `null`（未决 ≠ 不回复）。

## 20. Decision Trace 与 Evidence

Trace 是**诊断**，不是路由输入；只读导出，字段白名单，不含正文与自由文本推理：

```json
{
  "routing_schema_version": 2,
  "mode": "legacy",
  "topic": {"topic_id": "T3", "confidence": 0.64, "ambiguous": true},
  "recipient": {"ids": ["bot"], "bot_targeted": true, "confidence": 0.95, "ambiguous": false},
  "identity": {"bot_reference": "vocative", "mention": false, "vocative": true, "subject": false},
  "participation": {"score": 0.95, "level": "strong", "should_reply": true},
  "state": {"active_interlocutor": "user_a", "pending_hover": false, "intervening_users": 0},
  "weights_version": "recipient-v2"
}
```

已修的问题：`topic_ambiguous` 与 `recipient.ambiguous` 现在各自独立输出，consistency
用例（`tests/test_recipient_ambiguity.py`）锁定“话题不确定不改变收件人结论”，
双向（Bot / 人类收件人）都覆盖。回放在隐藏内容时清空收件人 ID、隐藏对话对象、
把中间发言者降级为计数。

**尚未完成**：evidence 仍是“推理过程中发生过什么”的字符串列表，没有拆成结构化
`Evidence(code, family, strength, source)`；评估器与回放面板目前只读最终字段。
这是 §21 数据积累后的工作。

## 21. Shadow 模式

Shadow 不能“旧 resolver 跑一次、新 resolver 再跑一次”并让两者都改 DAG/runtime，否则
是双系统互相污染。正确形式：

```text
immutable snapshot → legacy evaluate → new evaluate(commit=False) → compare
```

Shadow 实现必须只读：不改 pending_hover、不改 DAG、不改 active dialogue、不改 topic。
本版的落地方式是不引入第二个可写路由器，而是：

- 用**改前源码快照**跑同一夹具得到基线（`docs/routing_baseline.json`，只读比较）；
- `RecipientResolver.infer` 为纯函数并已有“无副作用”断言测试；
- 线上沿用既有 `shadow_mode` 开关记录预测动作而不发送。

## 22. 人工标注 schema v2

现有话题标注不足以训练 Recipient，本版扩展为 schema v2（`annotation_schema_version: 2`），
在原四字段之外支持：

| 字段 | 含义 |
| --- | --- |
| recipient_correct | 收件人推断是否正确 |
| bot_targeted | 是否在对 Bot 说话 |
| recipient_ids | 收件人 ID 集合（去重，≤64 项） |
| subject_ids | 被讨论对象 ID 集合 |
| expected_reply | 是否应该回复 |
| recipient_error_type | `correct` / `missed_bot` / `false_bot` / `wrong_recipient` / `missing_recipient` / `subject_confusion` / `unknown` |

与讨论稿的命名映射：

```text
BOT_TARGET_FALSE_NEGATIVE → missed_bot
BOT_TARGET_FALSE_POSITIVE → false_bot
WRONG_RECIPIENT           → wrong_recipient
MULTI_RECIPIENT_DROPPED   → missing_recipient
SUBJECT_AS_RECIPIENT      → subject_confusion
RECIPIENT_AS_SUBJECT      → subject_confusion
CONTINUATION_MISSED / AMBIENT_INTRUSION → 暂由 missed_bot / false_bot + expected_reply 组合表达
```

保存时深拷贝话题诊断与白名单 trace 快照，实时状态改变不会改写已标注记录；默认不保存
正文，只有 `console_show_message_content=true` 时才保存最多 2000 字。GET 在原有
`metrics` 之外新增独立的 `recipient_metrics`，旧记录不会被计入收件人样本。

## 23. Evaluator：数据来源与可复现性

第一阶段不等真实标注积累，先用**合成 golden 用例 + 现有测试场景 + 人工挑选片段**建立
确定性基线（`tests/fixtures/routing_golden.json`）。运行方式：

```bash
python scripts/evaluate_routing.py --output docs/routing_current.json --check
python scripts/evaluate_routing.py --baseline docs/routing_baseline.json
```

风险与对策：

- **import 正确性**：仓库存在被 `.gitignore` 忽略的嵌套旧副本。评估器把仓库父目录
  放在 `sys.path` 首位，并断言加载到的 `thread_router` 就是仓库根目录文件，
  否则宁可报错也不静默测旧代码。
- **可复现性**：固定时钟、固定夹具、关闭神经服务、固定阈值；报告带
  `config_hash`、`fixture_hash`、`weights_version`，同一次 replay 可重复比对。
  配置哈希只覆盖评估器设置，不是源码校验和。
- **只读**：`--output` 不得覆盖 `--baseline`/`--fixtures`；比较只读，不修改任何一侧。
- **比较口径**：只比较双方都记录过的字段，新增字段不会被误报成行为变化；失败数变化
  单列 `failed_delta`。

## 24. 指标

**Recipient**：Explicit Bot Target Recall / Precision、Continuation Recall / Precision、
Bot Target FN / FP、Multi-recipient Accuracy。不能只追 overall recall，必须分场景。

**场景取向**：

```text
明确叫 Bot（@Bot / 引用 Bot / 明确呼语） → Recall 接近 100%，FN ≈ 0
Bot 与用户持续对话                      → 高 Recall，同时控制他人误继承
Ambient 主动插话                        → Precision 优先，不因降 FN 而到处插话
```

**Topic**：Assignment Accuracy、New Topic Precision / Recall、Wrong Merge Rate、
Fragmentation Rate、Archived Topic Reopen Accuracy。Wrong Merge 通常比暂时 UNKNOWN 更
危险，因为错误合并会持续污染后续 context。

**Parent**：Parent Accuracy / Coverage。`然后呢 / 为什么 / 那这个呢` 的归属应更多依赖
parent 与对话血缘，而不是 embedding。

**本版已采集 / 未采集**：

| 指标 | 状态 |
| --- | --- |
| Golden Recipient 混淆矩阵（legacy/persona） | 已采集（14 例，见 §0） |
| 收件人层级 strong/hover/weak | 已采集（每例锁定，含旁观 hover） |
| Topic Wrong Merge / Fragmentation | 未采集（缺话题标签） |
| Parent Accuracy | 未采集 |
| 路由 p50 / p95 延迟 | 未采集（沿用讨论中的量级观察，未复测） |
| Prompt 字符/token | 部分（统一 1200 字/条上限，未统计总量） |
| Embedding 调用数 / 超时率 | 未采集（已有并发上限与代次隔离） |

未采集项在 annotation v2 积累真实样本后补齐；在此之前不据此调整权重。

## 25. Golden 回归清单

必须锁死的既有行为（Regression Locks）：

```text
@Bot 帮我看看              → STRONG
回复 Bot：那这个呢          → STRONG
Bot → A，A：然后呢          → STRONG
@小明 你怎么看              → Bot WEAK，收件人 [human]
回复 A：群间你看看他说得对不对 → Bot 应回复
助手席怎么拆（Bot 名=助手）   → 不应认为是 Bot 呼语
显卡怎么选（Bot 名=卡）       → NONE
群间刚才说的方案不太对        → 讨论对象，不是呼语
```

§3 讨论中的关键用例已全部进入夹具，其中“多收件人”“话题歧义不影响收件人”
“单字呼语/子串负例”“旁观短句不继承对话且 persona 不认领”为新增覆盖；
“引用他人但在对 Bot 说话”保留为 `human_quote_bot_vocative`，其中被引用的他人以
parent 上下文形式保留，`subject_ids` 仍只表示对参与者的第三人称指涉。

## 26. 开发顺序与验收

```text
PR0   Observability：Trace / 回放只读导出 / 固定基线 / Golden / import 断言 / 双模式
PR0.1 Ambiguity Hotfix：topic ≠ addressee 歧义，并清理陈旧 evidence 口径
PR1   Recipient Schema v2：BotIdentityMatcher / RecipientInference / 多收件人 / 短昵称策略
PR2   ParticipationPolicy：Addressivity 不再自行判断 recipient（部分落地）
PR3   Annotation Schema v2 + Evaluator（已落地）
PR4   Canonical Prompt Context（已落地）
PR5   Topic Profile Revision（经核查不必要；仅做输出等价优化）
PR6   Embedding Execution（已落地执行上限/代次/归属）
PR7   Optional Topic Top-K（需 R@K guard，本版不做）
```

对真实群聊体验收益最大的是 Ambiguity Hotfix + Recipient v2 + Participation v2；
对性能最安全的是 Topic Profile 核查 + Prompt Context 去重；Top-K、增量 centroid、
大规模 main.py 重构都必须后置。

## 27. 配置 Flag 策略（偏差说明）

讨论稿建议为新行为提供 `recipient_v2_enabled` 等阶段性开关。本版**没有**新增开关，
理由：

1. Recipient v2 是对既有字段的语义修正，不是并行算法；同一进程内同时存在两套收件人
   结论会让“谁说了算”重新变得不可判定。
2. 本版已有更可靠的护栏：固定夹具 + 只读基线比较 + 真实生产实现参与评估 +
   线上 `shadow_mode`。
3. 新增配置项会写进 `_conf_schema.json` 并进入面板，属于面向用户的长期承诺，
   不应为一次性迁移而增加。

若后续某次改动确实无法用夹具锁定（例如更换 embedding 模型、上线 Top-K），再引入开关。

## 28. 本版不做的事

```text
大规模拆 main.py
完全重写 Topic 系统
同时更换 embedding 模型
新增第二层 LLM recipient classifier
大规模增加关键词规则
直接删除旧 Addressivity 回退
立刻做 incremental centroid
未经 R@K 测试就上 Topic Top-K
在没有标注数据时调软证据权重
```

当前最需要的是语义契约稳定、行为可测、错误可定位，而不是继续扩大系统复杂度。

## 29. 优化前后的核心变化

```text
优化前
  “在聊什么”“在对谁说”“Bot 应不应该回答”在多个模块中互相穿插
  一个 Topic ambiguity 可以否决明确的 Recipient
  一个名字 substring 可以污染 Subject
  一个 Addressivity score 同时承担 recipient + participation
  下游再各自解释

优化后
  BotIdentityMatcher   → 识别 Bot 在语言中的身份（mention / vocative / subject）
  RecipientResolver    → 只回答“在对谁说”
  TopicResolver        → 只回答“在聊什么”
  Addressivity/Arbiter → 只回答“Bot 要不要开口”
  Context Builder      → 只负责把结论整理成唯一 payload
```

## 30. 最终目标架构原则

1. `Recipient ≠ Topic`：话题不确定不能否决明确收件人。
2. `Subject ≠ Addressee`：提到 Bot 不等于叫 Bot。
3. `Similarity ≠ Addressivity`：embedding 能证明“像之前那个话题”，不能证明“在对 Bot 说”。
4. `Participation ≠ Recipient`：“是不是在叫 Bot”和“Bot 值不值得开口”必须是两层。
5. `No metrics → No routing rewrite`：任何路由改动先具备 baseline、decision trace、
   golden tests，再谈权重。

## 31. 结论

v1.4.2 不追求“模型更聪明”，而是让正确的信号只负责正确的问题、并且不再互相否决。
Recipient / Topic / Participation 解耦之后，后续无论是更好的 embedding、更强的 topic
reranker，还是用真实人工标签拟合参数，都建立在可测、可解释、可回归的架构上。

本版已验证的部分（歧义解耦、身份统一、多收件人、上下文统一、Embedding 上限、
回放与标注）都有确定性回归覆盖；未验证的部分（ParticipationPolicy 证据族、
ActiveDialogue 显式状态、结构化 Evidence、Topic/Parent 指标、Top-K）已在文中逐项
标注为缺口，并给出各自的准入条件。
